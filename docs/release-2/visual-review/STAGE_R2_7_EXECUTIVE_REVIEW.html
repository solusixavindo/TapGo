02 Arsitektur & Alur Pembelian backend runtime

Alur dua fase: debit atomik di dalam transaksi serializable, pemanggilan provider setelah commit, finalisasi dengan kompensasi.

Client + Idempotency-Key→ Zod validator→ PpobService.purchase→ TX: debit bersyarat + ledger + PENDING→ commit→ provider.purchase→ finalize: SUCCESS / FAILED+refund

Jaminan aman-uang

  • Debit ganda mustahil — @@unique([userId, idempotencyKey]) + ras P2002 diselesaikan ke transaksi pemenang.
  • Refund ganda mustahil — transisi bersyarat status non-final + cek ledger PPOB_REFUND sebelum kredit balik.
  • Saldo negatif mustahil — updateMany dengan klausa ppobBalance >= total di bawah row lock.
  • Sukses tanpa bukti mustahil — kegagalan proses antara commit dan provider menyisakan PENDING yang dapat direkonsiliasi, bukan SUCCESS palsu.
Keputusan: provider nyata (Digiflazz dsb.) bukan lingkup stage ini. Port dibekukan agar R2.8 tinggal menambah adapter tanpa menyentuh service/repository/refund.

08 Limitasi & Rollback dikenali

  • Adapter stub sinkron-sukses; status PROCESSING dicadangkan untuk fulfillment asinkron R2.8.
  • PLN Pascabayar & BPJS di-seed nonaktif — harga tagihan butuh inquiry provider nyata (R2.8).
  • Belum ada worker rekonsiliasi transaksi PENDING yatim (R2.8).
  • Belum ada endpoint admin PPOB (R2.9 Unified Admin).
  • Surface Play tidak berubah; aktivasi menu Play adalah keputusan R2.9.

Rollback

  • Flutter: revert commit — label Pulsa kembali ke _showSoon.
  • Backend: hapus mount /api/v1/ppob dari app.ts; tabel baru tidak dibaca modul lain.
  • Database: DROP TABLE ppob_transactions, ppob_products; DROP TYPE PpobCategory, PpobTransactionStatus; — nilai enum wallet baru dibiarkan (tidak dapat di-drop di Postgres; tidak dipakai baris lama).
